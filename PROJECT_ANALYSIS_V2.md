## 1. КРАТКОЕ РЕЗЮМЕ

**Что это:** Telegram-бот для группового чата. Ведёт себя как «живой парень» — шутит, помогает, подкалывает, может огрызаться.

**Технический стек:**
- Python 3.8+, `python-telegram-bot` 21.x
- AI: DeepSeek API (через OpenAI SDK)
- БД: Firebase Firestore (сообщения, юзеры, граф знаний)
- Гифки: Giphy API
- Деплой: Railway / Render

**Архитектура (компоненты):**
| Компонент | Файл | Роль |
|-----------|------|------|
| Точка входа | `main.py` | `DeepSeekBot` — связывает всё вместе |
| Конфиг | `config.py`, `models.py` | Загрузка `.env`, типизированный `BotConfig` |
| Память | `memory.py` | Краткосрочная (RAM) + долгосрочная (Firebase) + daily_log |
| Мозг | `brain.py` | Решение «отвечать?», классификация сложности, генерация ответа |
| Ответы | `responder.py` | Отправка текст/реакция/гифка/стикер |
| Промпты | `prompts.py` | Системный промпт персоны + контекст |
| **Граф знаний** | `graph_memory.py` | Факты о юзерах по категориям |
| **Ночной анализ** | `deepseek_analyzer.py` | DeepSeek-R1 извлекает факты из чата |
| Планировщик | `night_analyzator.py` | Запуск анализа в 3:00 |

## 2. АРХИТЕКТУРА

### Поток обработки сообщения (сейчас)
```
Сообщение в чат
  → main.handle_message()
    → фильтры (боты, chat_id)
    → memory.add_message()        ← сохраняем в short-term + daily_log + Firebase
    → brain.should_respond() / smart_should_respond()
       ├── упоминание имени? → да
       ├── continuation trigger + отвечал недавно? → да
       ├── есть "?" ? → да
       └── random 10% → да
    → brain.generate_response()
       ├── RequestClassifier.classify() → сложность → токены/температура
       ├── knowledge_manager.get_relevant_context_for_message()  ← граф знаний
       └── DeepSeek API → текст ответа
    → responder.send_response()
       └── ResponseParser.parse() → TEXT / REACT / GIPHY / STICKER
```

### Поток ночного анализа
```
3:00 (планировщик)
  → NightlyAnalysisTask.run()
    → DailyMessageCollector.get_yesterday_messages()
       ├── Firebase: where date == yesterday
       └── fallback: memory.get_daily_log()  ⚠️ см. баг №1
    → DeepSeekAnalyzer.run_nightly_analysis()
       └── для каждого юзера: analyze_user_messages()
          └── deepseek-reasoner извлекает факты → graph → Firebase
    → отчёт в чат
    → clear_cache() + clear_daily_log()
```

## 3. ПРОБЛЕМА №1 — ЗНАНИЯ О ЛЮДЯХ

> *«каждую ночь дип сик r1 анализировал весь чат за день и собирал факты о людях… но по факту очень мало раз когда он такое делал или я не замечал и факты вытаскивались очень странные»*

Я нашёл **КОРНЕВЫЕ ПРИЧИНЫ**, почему идея не работает на практике:

### 🔴 Причина 1.1: Граф знаний почти НИКОГДА не попадает в ответ

Это главная проблема. Смотри цепочку:

**Запись фактов (работает):** ночной анализ → `graph.add_fact()` → Firebase ✅

**Чтение фактов (сломано):** `brain.generate_response()` →
```python
kg_context = self._knowledge_manager.get_relevant_context_for_message(
    user_id=user_id, message_text=message_text, username=...
)
```

Внутри `get_relevant_context_for_message()`:
```python
topics = self._topic_detector.detect_topics(message_text)  # ← Detect ТОЛЬКО из текущего сообщения!
graph = self.get_user_graph(user_id, username)
return graph.get_relevant_context(topics)
```

**Проблема:** `TopicDetector.detect_topics()` ищет ключевые слова в **текущем сообщении**. Если пользователь сейчас пишет «привет, как дела» — детектор тем возвращает `GENERAL`, а в графе факты лежат в категориях `gaming/food/...`. → `get_relevant_context()` возвращает **пустую строку**. → Граф не попадает в промпт. → Бот «не помнит» ничего.

Чтобы граф сработал, нужно совпадение: пользователь должен прямо сейчас заговорить о теме, которая есть в графе (например, сказать «дота»), и тогда подтянутся его же факты про «дота». Это почти никогда не совпадает с моментом, когда было бы уместно вспомнить факт о человеке.

### 🔴 Причина 1.2: Категории анализатора ≠ категории детектора тем

В `deepseek_analyzer.py` промпт просит вернуть факты в категориях:
```
gaming, food, movies, sports, music, work, other
```

Но `TopicCategory` enum (в `graph_memory.py`) содержит:
```
gaming, food, education, work, entertainment, social, tech, sports, music, travel, general
```

**Несоответствия:**
- Промпт просит `movies` → `TopicCategory("movies")` → `ValueError`! → код ловит исключение и кидает факт в `GENERAL` (`other`→`general`).
- Промпт просит `other` → тоже падает в `general`.
- А `education, entertainment, social, tech, travel` — анализатор их вообще никогда не возвращает, хотя ключевые слова для них есть в `TOPIC_KEYWORDS`.

**Итог:** факты про фильмы (`movies`) оказываются в категории `general`, и когда детектор тем находит тему «кино» (`entertainment`), он не находит фактов, потому что они лежат в `general`. **Двойная рассинхронизация.**

### 🔴 Причина 1.3: Факты «странные», потому что нет фильтрации качества

Промпт анализатора пишет «извлекай только постоянные характеристики», но `deepseek-reasoner` с температурой по умолчанию всё равно:
- галлюцинирует (добавляет факты, которых не было)
- извлекает временные состояния («устал», «болеет»)
- обобщает («интересуется сложными играми» вместо «Dark Souls»)

Нет проверки: Confidence? Подтверждён факт из нескольких сообщений или из одного? Нет дедупликации по смыслу (только по точной строке).

### 🔴 Причина 1.4: Граф только про 1 юзера (того, кто пишет)

`generate_response()` передаёт `user_id` одного текущего отправителя. Но в групповом чате уместно вспомнить факт и о ДРУГОМ человеке («а вот Вася же говорил, что любит доту»). Сейчас это невозможно — контекст строится только про автора сообщения.

### 🔴 Причина 1.5: daily_log живёт только в RAM и чистится после анализа

`clear_daily_log()` в `NightlyAnalysisTask` удаляет сообщения после анализа. Если бот перезапустился ДО 3:00 — daily_log пустой с нуля (он в RAM). Firebase-источник работает только если поле `date` корректно сохранено. То есть данные для анализа хрупкие.

## 4. ПРОБЛЕМА №2 — БАЛАНС СТИКЕРОВ/ГИФОК VS ТЕКСТ

> *«часто бывало такое что у него что то спрашиваешь а он кидает гифку или стикер а когда хочешь гифку то он пишет текст»*

### 🟡 Причина 2.1: Сейчас это частично «выключено», но корень остался

В `config.py` дефолт `TEXT_ONLY_MODE=true`. Это значит сейчас бот вообще шлёт только текст. Но ты явно хочешь вернуть гифки/стикеры, только чтобы они были **к месту**. Поэтому важно починить корень.

### 🟡 Причина 2.2: Решение о формате = только промпт, без обратной связи

Формат ответа (`TEXT/GIPHY/REACT/STICKER`) выбирает DeepSeek через системный промпт (`prompts.py`). Промпт говорит «~85% текст, ~8% гифка» — но модель НЕ знает:
- сколько гифок она уже скинула за последние N сообщений
- что пользователь ПРОСИЛ гифку прямо сейчас (если он написал «дай гифку», это часто теряется)

Нет **учёта явного запроса**: если пользователь пишет «скинь гифку» — это должно триггерить GIPHY принудительно, но промпт не гарантирует, что модель это услышит.

### 🟡 Причина 2.3: ResponseParser + Responder не пытаются «исправить» несоответствие

В `_send_reaction()` есть умная логика (проверяет `REACTION_KEYWORDS` / `TEXT_KEYWORDS` в сообщении). Но для GIF и STICKER такого нет — нет проверки «юзер просил гифку → а модель вернула текст» или «юзер задал вопрос → а модель вернула гифку».

### 🟡 Причина 2.4: StickerManager всегда шлёт СЛУЧАЙНЫЙ стикер

```python
if self._all_stickers:
    return random.choice(self._all_stickers)
```
Эмоция из ответа (`STICKER:happy`) **игнорируется**, если загружен стикерпак. Значит даже когда бот «хотел» послать грустный стикер, летит случайный. Это убивает смысл эмоций.

## 5. ПРОБЛЕМА №3 — СТИЛЬ, МОМЕНТ ОТВЕТА, «НЕ УМЕЕТ ПОСТОЯТЬ ЗА СЕБЯ»

> *«не всегда понимал в каком стиле ответить и не всегда понимал когда именно нужно отвечать. еще не умел за себя постоять»*

### 🟠 Причина 3.1: «Когда отвечать» — эвристики костыльные

Две ветки:
- `should_respond()` (эвристики): имя / continuation / `?` / random 10%.
  - **Слишком агрессивно:** любой `?` = ответ. Любой «ещё» после ответа = ответ.
  - **Слишком пассивно:** обычная болтовня, где уместно вписаться, — пропускается (только 10% random).
- `smart_should_respond()` (AI): лучше, но **дефолтно выключен** (`USE_SMART_RESPOND=false`). И даже он не видит «кто пишет», «обращаются ли к боту по смыслу», историю за весь день.

### 🟠 Причина 3.2: «В каком стиле» — стиль не определяется как отдельный шаг

Стиль (шутник/помощник/подколыщик/ответочка) **захардкожен в системный промпт** как «выбирай сам, ~25% каждый». Нет отдельной классификации: «это вопрос о помощи → помоги», «на меня наехали → ответочка», «все смеются → подкол». Модель должна сама угадывать из контекста — иногда угадывает, иногда нет.

### 🟠 Причина 3.3: «Не умеет постоять за себя»

В промпте есть блок **«🔥 Ответочка»**, но:
1. Нет **детекции** «на меня наехали». Модель должна сама понять это из контекста.
2. DeepSeek по умолчанию «вежливый» — безопасности модели мешает материться/унижать, даже если промпт просит. Температура/настройки не форсируют это.
3. Нет «памяти обид» — бот не помнит, кто его недавно оскорблял, чтобы реагировать острее на конкретного юзера.
4. Ответочка сидит **в том же промпте** на 25% с остальными ролями — модель «усредняет» и часто выбирает безобидный вариант.

## 6. ДОПОЛНИТЕЛЬНЫЕ СКРЫТЫЕ ПРОБЛЕМЫ

Эти я нашёл по ходу — они не из твоего списка, но важны для V2:

### ⚠️ Баг №1: Временной баг ночных данных (critical для проблемы №1)
`NightlyAnalysisTask` регистрируется на 3:00. Но `_get_next_run_time`/`_run_scheduler` имеют тонкий момент: проверка `abs(target_minutes - current_minutes) <= 1` + проверка `last_run.date() < now.date()`. Если бот **перезапустился после 3:00**, задача в этот день уже не запустится (last_run нет, но target уже прошёл → ждёт завтра). Плюс `clear_daily_log()` оставляет только «сегодня» — а анализ идёт по «вчера». Если в 3:00 daily_log уже обнулён — анализ пойдёт по пустому логу (только Firebase спасает).

### ⚠️ Баг №2: `run_hour`/`run_minute` не берутся из конфига
В `main.py` хардкод `run_hour=3, run_minute=0`, хотя в `BotConfig` есть `nightly_analysis_hour/minute`. Меняй в `.env` — не работает.

### ⚠️ Баг №3: `deepseek_model` в config = `deepseek-v4-flash`, но анализатор хардкодит `deepseek-reasoner`
`config.py` дефолт `deepseek-v4-flash`. Это значит, что основной чат использует не ту модель, что описана в README (`deepseek-chat`). Убедись, что эта модель существует в твоём API-аккаунте, иначе будут ошибки.

### ⚠️ Баг №4: `responses.py` (responder) — `_send_reaction` ignores parsed emoji when text-fallback
Если реакция падает, он шлёт эмодзи текстом. Но эмодзи как текст в ответ на вопрос — выглядит странно.

### ⚠️ Баг №5: `new_facts` прикручивается к графу, но это не поле dataclass
`graph.new_facts = new_facts` — динамический атрибут. Работает, но хрупко и может ломать `to_dict()` при сериализации, если случайно сериализовать.

### ⚠️ Баг №6: Нет rate-limit / очереди на DeepSeek API
Ночной анализ бьёт по API последовательно, но в паблике с 10+ юзерами это длинный цикл дорогих reasoner-запросов. Нет ретраев, нет backoff. Один сбой → пользователь без обновления графа.

### ⚠️ Баг №7: `chat_id` фильтр — только один чат
Бот работает только в одном `CHAT_ID`. Для V2, если захочешь несколько чатов — архитектура memory/graph завязана на единое пространство.

### ⚠️ Баг №8: `requests.post` в async-функции (анализатор)
`analyze_user_messages` — `async def`, но внутри `requests.post(timeout=120)` — **синхронный блокирующий вызов**. На время анализа (до 120с) бот **зависает** и не отвечает на сообщения в чате. Нужно `aiohttp` или `asyncio.to_thread`.

### ⚠️ Баг №9: Безопасность — `.env` с реальными ключами в репозитории
Я вижу `.env` (5177 байт) в папке проекта. Проверь, добавлен ли он в `.gitignore` и **не запушен ли** на GitHub. Если запушен — **немедленно сменить все ключи** (Telegram, DeepSeek, Giphy, Firebase).

### ЭТАП 1 — Починить знания о людях (Проблема №1) ⭐ главный приоритет
Это самая ценная фича, и её можно сделать реально работающей.

**Концепция V2:** вместо «категории по ключевым словам» — **семантический поиск** + **явные триггеры**.

| # | Задача | Что даёт |
|---|--------|----------|
| 1.1 | Синхронизировать категории: единый список категорий в одном месте (модуль `categories.py`), использовать и в анализаторе, и в детекторе тем | убирает Причину 1.2 |
| 1.2 | **Сменить парадигму извлечения фактов**: не «детектим тему по слову», а **всегда** передавать в промпт краткую сводку ВСЕХ фактов о ВСЕХ юзерах чата (компактно) | убирает Причину 1.1 |
| 1.3 | Передавать факты не только об авторе, но и о **всех юзерах чата** (кто упоминается) | Причина 1.4 |
| 1.4 | Добавить **confidence / evidence** к фактам: сколько раз замечено, ссылка на сообщение-источник | убирает «странные факты» (1.3) |
| 1.5 | Промпт анализатора: просить ВСЕ факты + явные примеры «что НЕ факт», +2-3-shot примеры, требовать source quote | качество (1.3) |
| 1.6 | Дедупликация по смыслу (не по точной строке) — например, через embeddings или нормализацию | чистота графа |
| 1.7 | Очередь анализа + идемпотентность (не терять данные при рестарте) | Баг №1 |
| 1.8 | Команда `/profile @user` — показать, что бот знает о человеке (для отладки и «вау») | наглядность |

**Альтернатива (продвинутая):** подключить **LightRAG / векторную память** (в `.env` уже заложен `OPENAI_API_KEY` для embeddings). Тогда факты хранятся как векторная база, и bot достаёт релевантные по смыслу к текущему контексту, а не по совпадению ключевых слов. Это самый «правильный» путь для V2.

### ЭТАП 2 — Баланс стикеров/гифок vs текст (Проблема №2)

**Концепция:** формат ответа = **явный intent-слой**, а не «модель сама решит».

| # | Задача | Что даёт |
|---|--------|----------|
| 2.1 | **Intent-парсер**: перед генерацией проверять сообщение на явные запросы гифки/стикера/текста (`дай гифку`, `поставь реакцию`, `скинь стикер`) | Причина 2.2 |
| 2.2 | Если intent = «хочет гифку» → принудительно генерировать `GIPHY:` (или после ответа, если был intent, а модель дала текст — перегенерить/переопределить) | Причина 2.3 |
| 2.3 | **Трекер форматов**: помнить последние N форматов, в промпт добавлять «ты скинул N гифок подряд, теперь текст». Глобальный баланс | Причина 2.2 |
| 2.4 | Починить `StickerManager`: учитывать эмоцию, а не случайный стикер (маппинг эмоция→file_id) | Причина 2.4 |

## 8. ПРЕДЛОЖЕНИЯ ПО АРХИТЕКТУРЕ

### Предлагаемая схема pipeline V2

```
Сообщение
  → Фильтры
  → memory.add_message()
  → [Шаг 1] Intent & Situation layer
       ├── detect_gif_request / detect_sticker_request / detect_text_request
       ├── detect_attack_on_bot (→ defend mode)
       └── situation = SituationClassifier(message, context, graph)
  → [Шаг 2] should_respond (smart, видит ситуацию)
       └── если detect_attack → ВСЕГДА отвечать
  → [Шаг 3] context_builder
       ├── последние сообщения
       ├── KB summary (семантический топ-K фактов по всему чату)
       ├── «память обид» если есть
       └── tracker: последние форматы (для баланса)
  → [Шаг 4] generate_response (промпт под situation, format hint из intent)
  → [Шаг 5] format guard
       ├── если контент-вопрос, а ответ — стикер → перегенерить текстом
       └── если был gif-request, а ответ текст → перегенерить гифкой
  → responder.send_response()
```

### Новый файл `api_client.py`
Вынести весь DeepSeek в один async-клиент с:
- ретраями (exp backoff)
- таймаутами
- двумя моделями: fast (решение «отвечать?», классификация) и main (генерация)
- опционально reasoner (анализ)

### Единый источник категорий — `categories.py`
Чтобы анализатор и детектор тем больше не рассинхронизировались.

### Хранение графа (выбор)
- **Минимум:** текущая Firestore-структура, но: (а) единые категории, (б) всё facts в контекст компактно, (в) confidence.
- **Максимум:** embeddings + vector store (LightRAG). В `.env` уже есть `OPENAI_API_KEY`.

## 9. СВОДНАЯ ТАБЛИЦА: проблема → решение

| Проблема | Корень | Решение V2 | Этап |
|----------|--------|------------|------|
| Граф не используется | TopicDetector по текущему сообщению → пусто | Всегда передавать компактную KB-сводку по всем юзерам | 1.2 |
| Несовпадение категорий | `movies/other` падают в general | Единый `categories.py` | 1.1 |
| Странные факты | нет фильтра качества | confidence + evidence + few-shot промпт | 1.4–1.6 |
| Граф только про автора | user_id одного юзера | facts по всем юзерам чата | 1.3 |
| Гифка вместо ответа | нет intent-слоя | Intent-парсер + format guard | 2.1–2.5 |
| Случайный стикер | random.choice игнорит эмоцию | маппинг эмоция→file_id | 2.4 |
| Не понимает когда отвечать | костыльные эвристики / smart выключен | smart_should_respond по умолчанию + situation | 3.1–3.2 |
| Не понимает стиль | один гигантский промпт | situation → микро-промпты | 3.2–3.3 |
| Не постоять за себя | нет детекции наезда + safety | attack detector + отдельный промпт ответочки + память обид | 3.4–3.7 |
| Бот зависает на анализе | requests.post в async | aiohttp | 0.3 |
| Ночные данные теряются | clear_daily_log + restart | очередь + идемпотентность | 1.7 |
| `.env` в git | — | проверить/ротация | 0.1 |
